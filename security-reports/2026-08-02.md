## Findings & Actions Taken

### 🚨 CRITICAL — `create-razorpay-order` has no authentication check
`supabase/functions/create-razorpay-order/index.ts` accepts any POST request bearing only the **public anon key** (no user JWT verification, no `Authorization` user check beyond the platform's own apikey gate) and creates a real Razorpay order via the Razorpay API. Confirmed live during this run's mandated smoke test:
```json
{"order_id":"order_TKjtAd31tI3Z1i","amount":29900,"currency":"INR"}
```
This means:
- Anyone with the anon key (which ships inside the public app bundle) can spam this endpoint to create unlimited real Razorpay orders — no user identity, no per-user rate limit, no idempotency tied to a subscription record.
- CORS is `Access-Control-Allow-Origin: *`, so any website can trigger it from a browser too.
- No money moves on order creation alone (Razorpay orders aren't charged until payment completes), but this is an abuse/DoS vector against your Razorpay account (order volume, dashboard pollution, potential fraud reconnaissance) and should require a verified Supabase auth JWT before calling Razorpay.
- **This was not auto-fixed** — editing payment-flow logic is out of scope for this audit's auto-fix rules and needs your review of the intended auth flow before shipping a fix.

### ℹ️ INFO — `profiles` SELECT policy is `true` (any authenticated user, not just the row owner)
The audit brief's literal spec said "profiles: users can only read/write their own row." The actual policy is `profiles are viewable by authenticated users` (`qual: true`) — any logged-in user can read any profile row. Unauthenticated reads are still blocked (confirmed in Check 2). This is almost certainly intentional — a dating app needs to show other users' profiles to swipe on — and precise location data is correctly kept separate in `profile_locations` with its own owner-only policy. Flagging only so you can confirm no unintended PII (beyond what a candidate card should show) lives in `profiles`.
