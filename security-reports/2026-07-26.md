## Findings & Actions Taken

### 🚨 CRITICAL — `create-razorpay-order` edge function has no authentication or rate limiting
File: [supabase/functions/create-razorpay-order/index.ts](supabase/functions/create-razorpay-order/index.ts)

The function never checks for a Supabase user JWT — it only reads `plan` from the body and immediately calls the Razorpay Orders API using the founder's live `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET`. `Access-Control-Allow-Origin` is also `*`. I ran the smoke test specified in the audit (anon key only, no user session) and it returned **HTTP 200 with a real order**, not the 400 the checklist expected:

```
curl -X POST .../functions/v1/create-razorpay-order -H "Authorization: Bearer <anon key>" -d '{"plan":"monthly"}'
→ 200 {"order_id":"order_THyARDkjIW7eqw","amount":29900,"currency":"INR"}
```

**Impact**: anyone who extracts the public anon key from the app bundle (trivial — it's meant to be public) can call this endpoint an unlimited number of times to create real orders against the founder's live Razorpay account. This does not move money by itself (no card is captured without completing Razorpay's checkout, and `verify-razorpay-payment` independently re-verifies the HMAC signature and the captured amount against Razorpay's own records before granting Premium — that function is correctly designed). The real risk is **abuse/cost/quota exhaustion and reconnaissance** against the Razorpay account: unlimited unauthenticated order creation with no rate limit and no linkage to a NearMatch user.

**Side effect of this audit**: the smoke test itself created one real (uncaptured) Razorpay order, `order_THyARDkjIW7eqw`, for ₹299. No payment was made against it.

Not auto-fixed — this is payment-integration code, outside the audit's auto-fix rules (which cover only `.env`, `.gitignore`, `npm audit`, and hardcoded secrets). Needs founder review before changing.
