## Findings & Actions Taken

### 🚨 CRITICAL — `create-razorpay-order` has no authentication check (carried forward, still unfixed)
File: `supabase/functions/create-razorpay-order/index.ts`. The function validates only HTTP method and request body shape (`plan` must be `monthly`/`quarterly`) — it never verifies a Supabase JWT / logged-in user. Live smoke test with only the anon key (no user session) succeeded and created a real order:
```
{"order_id":"order_TIlET07TRFAh4y","amount":29900,"currency":"INR"}
```
`Access-Control-Allow-Origin` is also still `"*"`. Anyone holding the (public, embeddable) anon key can spam-create real Razorpay orders with no rate limiting, which is an abuse/quota-exhaustion vector against the Razorpay account, not a direct fund-theft path (order creation ≠ captured payment) — but it is unverified and untested payment-adjacent code. Per the auto-fix rules, RLS/payment logic is not to be auto-changed. **No action taken — flagged for founder review**, same as the 2026-07-27 evening / 2026-07-28 morning reports.

### ⚠️ WARN — npm audit: 19 high, 8 moderate, no safe fix
`npm audit fix` (non-force, dry run confirmed) is a no-op — all 19 high-severity advisories (`expo`, `react-native`, and their toolchain deps) require `npm audit fix --force`, which would jump `expo` to 57.0.8 and `react-native` to 0.86.2 (both semver-major). AGENTS.md flags that Expo has changed significantly in this version range and instructs reading the v54 docs before writing code — forcing an untested major upgrade on a live app is out of scope for an automated fix. **No action taken — requires founder-scheduled upgrade + testing window.**

### ⚠️ WARN — Untracked migration risks DB drift (carried forward)
`supabase/migrations/20260725000001_security_fix_rpc_grants.sql` is untracked in git and **not present** in `supabase_migrations.schema_migrations` on the live DB. I verified directly via `information_schema.routine_privileges` that the grants it's meant to apply **are live and correct** right now (`get_user_id_by_email` restricted to `postgres`/`service_role` only; `is_premium` and `get_wallet_balance_paise` scoped to `authenticated`/`postgres`/`service_role`, no `anon`/`public` grants). So the fix is currently in effect, but since it isn't committed or migration-tracked, a DB rebuild or `supabase db reset` would silently drop it. **No action taken (git commit is a working-tree change decision for the founder, not a security auto-fix) — flagged for founder action.**

### ⚠️ WARN — No rate limit on swipes
`enforce_message_rate_limit` exists and covers `messages`. No equivalent function was found for `swipes` — only a unique index (`swipes_swiper_id_swiped_id_key`) prevents duplicate swipes on the same target, not high-frequency swiping in general. Low severity at current scale (19 total swipes across 10 profiles) but worth a founder note before any growth push.

As instructed by the audit checklist, the `create-razorpay-order` smoke test POST created a live order (`order_TIlET07TRFAh4y`, ₹299, no payment captured). This is a side effect of confirming the endpoint is unauthenticated, not a separate incident — flagging for transparency.
