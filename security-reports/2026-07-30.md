## Findings & Actions Taken

### 🚨 CRITICAL — `profile_locations` exposes exact GPS coordinates to any authenticated user
Two RLS policies on `public.profile_locations` grant `SELECT` to the `authenticated` role with `qual: true` (unconditionally true):
- `authenticated_select_profile_locations`
- `replace_with_policy_name` (literally an un-renamed template policy — strong signal this was never meant to ship as-is)

A correctly-scoped policy also exists (`users can manage their own location`, `user_id = auth.uid()`), but RLS policies are OR'd together — the two permissive ones fully override the restrictive one. Any logged-in user can run:
```
GET /rest/v1/profile_locations?select=*
```
and receive every user's exact `latitude`/`longitude`. This directly undermines the app's own privacy design — `get_candidate_profiles()` deliberately returns only a fuzzed distance bucket instead of raw coordinates, but the raw table is openly queryable regardless. For a dating app this is a real physical-safety/stalking risk, not just a data-hygiene issue.
**No auto-fix applied** — per standing instructions, RLS policy changes are never auto-modified. **Needs founder review and removal of the two `qual: true` policies immediately.**

### 🚨 CRITICAL — `create-razorpay-order` edge function has no authentication check
Smoke-testing with only the anon key (no user JWT, no `Authorization` header representing a logged-in user) and a made-up `{"plan":"monthly"}` body returned `200` and **created a real Razorpay order**: `order_TJYJcYluE0pG9D`, ₹299.00 (29900 paise), INR. No money was moved (order creation ≠ payment capture — the user would still need to complete checkout in Razorpay), but the function will apparently create orders for anyone who calls it, authenticated or not. This is an abuse vector (spamming Razorpay's API / polluting the order dashboard / potential rate-limit or cost exposure on the Razorpay account) and suggests the function isn't validating the caller's identity or session before hitting a paid third-party API.
**Founder action needed:**
1. Add an auth check (verify the caller's JWT / `auth.uid()`) to `create-razorpay-order` before creating an order.
2. Consider voiding/reviewing test order `order_TJYJcYluE0pG9D` in the Razorpay dashboard.

All remaining high-severity findings (`expo`, `react-native`, and their toolchain deps) only resolve via `npm audit fix --force`, which would force `expo` → 57.0.9 and `react-native` → 0.86.2 — semver-major changes on a live app. Not auto-applied. **Founder should schedule this as a planned upgrade** (test build + Expo v54 docs per `AGENTS.md` before touching this), not an unattended one.

### Minor — `referrals.replace_with_policy_name`
Same un-renamed template pattern as above, `qual: true`, `SELECT`, `authenticated` role. Effect is mostly redundant with the existing `users can view referrals they made` policy for read purposes, but it's still a blanket-read policy that shouldn't exist under that name. Recommend cleanup alongside the `profile_locations` fix.

### Minor — `profiles` table has a blanket-read policy
`profiles are viewable by authenticated users` (`qual: true`) lets any logged-in user read any profile row directly via REST, including profiles they've blocked or been blocked by (block enforcement only happens inside the `get_candidate_profiles` RPC, not at the base-table level). This may be intentional (e.g. for viewing a matched user's profile), but it does mean blocking someone doesn't stop them from directly querying the blocker's profile via `/rest/v1/profiles`. Flagging for founder awareness, not auto-changed.
