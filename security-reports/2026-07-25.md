## Findings & Actions Taken

### 🚨 CRITICAL — `get_wallet_balance_paise(p_user_id)` leaks any user's real-money wallet balance to anyone, unauthenticated
- **What I found:** The function body is `select coalesce(sum(amount_paise),0) from public.wallet_transactions where user_id = p_user_id` — it takes an arbitrary `p_user_id` parameter and never checks it against `auth.uid()`. It is `SECURITY DEFINER`, so it bypasses the `wallet_transactions` RLS policy (`user_id = auth.uid()`) entirely. `EXECUTE` is granted to both `anon` and `authenticated`.
- **Proof (live, confirmed this run):** Called `POST /rest/v1/rpc/get_wallet_balance_paise` with body `{"p_user_id":"c9adaa95-0c60-4f73-a6e8-eef59231bbcc"}` using **only the public anon key — no login, no user JWT** → returned `0` (that user's real wallet balance).
- **Impact:** Any UUID (leakable via the `profiles` table, which every authenticated user can already fully list) can be used to read that user's wallet balance in paise — real money-equivalent value used to buy Premium days. Direct privacy/financial-data breach.
- **Action taken:** ✅ FIXED 2026-07-25. Function body rewritten to always use `auth.uid()` (param ignored). `anon` explicitly revoked. Migration written to `supabase/migrations/20260725000001_security_fix_rpc_grants.sql`. Verified live: anon call now returns HTTP 401.

### 🚨 CRITICAL — `get_user_id_by_email(p_email)` is a public account-existence oracle
- **What I found:** `select id from auth.users where lower(email) = lower(p_email) limit 1` — `SECURITY DEFINER`, `EXECUTE` granted to `anon`. It's called internally by the `verify-razorpay-payment` edge function (legitimately, via a service-role admin fetch — that part is fine), but it is **also** directly callable by anyone through PostgREST's `/rest/v1/rpc/` endpoint.
- **Proof (live, confirmed this run):** `POST /rest/v1/rpc/get_user_id_by_email` with `{"p_email":"security-check@internal"}` using only the anon key → returned `null` for a non-existent test email (would return a real UUID for a registered one).
- **Impact:** On a dating app specifically, this is a sensitive class of leak — anyone can check whether a specific email address (an ex, a coworker, a public figure) has a NearMatch account, with no rate limit, no auth, no visible logging. Enables mass account-existence enumeration against a leaked/guessed email list.
- **Action taken:** ✅ FIXED 2026-07-25. Revoked from `anon` and `authenticated`, granted to `service_role` only. Migration written. Verified live: anon call now returns HTTP 404 (function not visible).

### ⚠️ MEDIUM — `is_premium(p_user_id)` leaks Premium subscription status for any UUID to anonymous callers
- Same pattern — `SECURITY DEFINER`, arbitrary `p_user_id`, granted to `anon`. Proof: anon call for a real user_id returned `false` with no auth. Lower severity than the wallet leak (boolean, not a monetary figure), but same root cause.
- **Action taken:** ✅ FIXED 2026-07-25. Function pinned to `auth.uid()`, `anon` revoked. Verified live: anon call now returns HTTP 401.

### ⚠️ WARN — `create-razorpay-order` edge function has no authentication or rate limiting
- **File:** [supabase/functions/create-razorpay-order/index.ts](supabase/functions/create-razorpay-order/index.ts)
- **What I found:** Accepts `{"plan": "monthly"|"quarterly"}` and immediately calls the real Razorpay Orders API with no caller-identity check and no rate limit.
- **Proof (live, confirmed this run):** Called with only the anon key → `HTTP 200`, `{"order_id":"order_THZh3sALpQ6KIH","amount":29900,"currency":"INR"}` — a real Razorpay order was created.
- **Context:** Consistent with the website's checkout flow, which (per comments in `verify-razorpay-payment/index.ts`) intentionally has no NearMatch login — so *some* unauthenticated access here may be by design. Unlike `verify-razorpay-payment` (protected by HMAC signature verification + a live Razorpay re-fetch before any money/Premium is granted), `create-razorpay-order` has zero abuse protection: no rate limit, no CAPTCHA, no session linkage. Can be spammed indefinitely to flood the merchant's Razorpay order list.
- **Action taken:** None — flagged for founder review.
- **Recommended fix:** Add a lightweight rate limit (e.g., by IP, or a short-lived token issued to the pricing page) before calling the Razorpay API.
