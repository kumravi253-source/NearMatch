## Findings & Actions Taken

### 1. `razorpay_order_attempts` — anon SELECT policy is fully open (WARN)
`pg_policies` shows `anon_select_razorpay_order_attempts` with `qual: true` — any holder of the anon key can `SELECT *` from this table with no row filtering. Table only contains `id`, `ip` (inet), `created_at` — used for the rate limiter, no user PII, name, or payment data. **Empirically tested with the anon key: currently blocked** (`42501 permission denied — GRANT SELECT ON public.razorpay_order_attempts TO anon` is missing), so there is no live exposure today. But the RLS policy itself is the wrong shape — a rate-limit bookkeeping table has no legitimate reason for anon SELECT (only INSERT is needed for the client path; the rate-limit function should read it as `service_role`/`security definer`). If a future migration or dashboard action adds the missing GRANT, every visitor's IP + timestamp history becomes world-readable via the anon key with no auth required. Not auto-fixed (RLS policy changes are founder-review-only per policy). **Flagged as CRITICAL for founder review**, since IP-address exposure at scale is a real privacy issue even without other PII.

### 2. npm audit: 11 high-severity vulnerabilities, no safe auto-fix (WARN)
All 11 (`expo`, `@expo/cli`, `@expo/metro*`, `metro*`, `react-native`, `@react-native/community-cli-plugin`, `@react-native/virtualized-lists`, `image-size`) require a semver-major bump — `expo` 53.0.27→57.x and `react-native` 0.72.17→0.81+. Ran plain `npm audit fix` first: it modified `package-lock.json` (pulled in an extra `@expo/metro-config@57.0.7` transitive entry) but **the vulnerability count did not change (still 11 high)** — the change fixed nothing, it just added lockfile noise. Reverted that change (`git checkout -- package-lock.json`) rather than commit a no-op diff. Did **not** run `npm audit fix --force`: that would force a major Expo/React Native version bump on a live production app's core framework, which is exactly the kind of hard-to-reverse, high-blast-radius change that needs a human decision, not an unattended one — especially since `AGENTS.md` in this repo explicitly flags that Expo's API has changed and to read the current version's docs before writing code against it. **Flagged for founder action.**

### 3. `create-razorpay-order` smoke test returned 200, not 400 (informational, not a bug)
The check script in this audit's instructions expected 400 for `{"plan":"monthly"}`. Investigation of `supabase/functions/create-razorpay-order/index.ts` shows `"monthly"` is a **valid** plan (400 is only for `invalid_plan`/`invalid_body`), and the function intentionally supports an anonymous ordering path (comment in source: "No auth.uid() available on this anonymous path, so this caps order..." — rate-limited by IP via the table in finding #1). So the 200 is correct behavior for a valid plan, not a security hole — but it means **this specific smoke test line item creates a real Razorpay order object and a row in `razorpay_order_attempts` every time it runs** (confirmed: row count was 2 before, includes today's test row). No money moves (creating a Razorpay order does not charge a card), but worth the founder knowing this check has a live side effect. No auto-fix applicable; noting for awareness only.
