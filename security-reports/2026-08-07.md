## Follow-Up 2 (same-session, root-cause investigation)

Founder asked to check the SQL Editor query history for what changed the function. Supabase's dashboard SQL Editor history itself isn't exposed via any Management API — it lives only in the dashboard UI, per-user, and isn't queryable programmatically. Two alternative sources were checked instead:

1. **Postgres logs (`postgres_logs` via the Logs/Analytics API):** `log_statement` is set to `ddl`, so DDL statements are logged in principle — but querying the logs endpoint returns 0 rows for any time range, including today. Log retention on this project's tier is short (1-3 days is typical on free/low tiers) and the events in question (08-02, 08-05, and even earlier today) have already aged out. This path is a dead end for anything older than a few hours.

2. **`pg_stat_statements` (has NOT been reset since 2026-08-02 02:55:32 UTC — covers the entire window of all three regressions):** This doesn't give exact timestamps, but it does retain the full, unique text of every distinct statement executed, with a call count. That surfaced the actual root cause:
   - The exact `CREATE OR REPLACE FUNCTION get_candidate_profiles(...)` text containing `cross join viewer_location v`, with the comment *"Same candidate logic as the proximity-matching migration, with one extra leading sort key: the candidate's own Premium status"*, has been executed **4 separate times** since 2026-08-02.
   - That exact text matches [`supabase/migrations/20260724000300_premium_gating.sql`](../supabase/migrations/20260724000300_premium_gating.sql) word-for-word — an old migration file from **2026-07-24**, more than a week before the first fix ever landed. It was written before anyone knew about the CROSS JOIN bug, so it never got the LEFT JOIN fix.
   - Critically, `supabase_migrations.schema_migrations` (the table `supabase db push`/`db reset` uses to track what's applied) still lists every fix migration — `20260802000002`, `20260805000000`, `20260806000000`, `20260806010000` — as applied, with no gaps and no re-insertion of `20260724000300`. A `supabase db reset` replaying the full migration history would have wiped and rebuilt that tracking table too; it didn't. That rules out a CLI-driven reset and points instead at **the raw contents of `20260724000300_premium_gating.sql` being executed directly against the database outside the migration pipeline** — almost certainly a saved SQL Editor snippet or an old local copy of that file being re-run by hand, not `supabase db push`/`db reset` and not any CI workflow (checked: no GitHub Actions, no seed/reset scripts, nothing in this repo references that filename).

**Most likely explanation:** someone has a saved snippet or local file with the pre-fix `premium_gating` SQL and has been re-running it directly in the SQL Editor (perhaps intending to "reapply the Premium sort feature" without realizing that specific copy predates the join fix), independent of git and independent of the Supabase CLI. This would explain why `schema_migrations` never shows drift — direct SQL Editor execution bypasses that table entirely — while the live function body keeps reverting to July 24's version.

**Recommended founder action:** check the Supabase dashboard's SQL Editor → History/Saved Queries for any saved snippet containing `cross join viewer_location` or the `premium_gating` comment text, and delete or correct it. If a teammate or automation has local access to an old checkout and runs SQL directly (e.g., via `psql` or a personal script) rather than through `git pull` + `supabase db push`, that's the other place to look. Until whatever is re-running this exact text is found and stopped, the fix applied earlier in this session should be treated as temporary.
