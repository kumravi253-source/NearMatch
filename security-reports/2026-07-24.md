## Findings & Actions Taken

### 🚨 CRITICAL — nearmatch.in is not serving the app
- `curl -sI https://nearmatch.in` returns HTTP 200 but the body/headers are from **GoDaddy's Website Builder** (`Server: DPS/2.0.0`, `X-SiteId: ap-south-1`, generator meta tag `"Starfield Technologies; Go Daddy Website Builder 8.0.0000"`, CSP referencing `godaddy.com`), not the React/Expo app.
- Netlify itself is healthy: site `tiny-dasik-a8f240` has `custom_domain: nearmatch.in`, `published_deploy.state: ready`, and the default Netlify subdomain (`https://tiny-dasik-a8f240.netlify.app`) correctly serves the real NearMatch app.
- Root cause: `nearmatch.in`'s nameservers are GoDaddy defaults (`ns49.domaincontrol.com`, `ns50.domaincontrol.com`) and the apex A records (`76.223.105.230`, `13.248.243.5`, both AWS/GoDaddy builder infra) are not pointed at Netlify. This means the domain's DNS was never delegated to Netlify (or was reset), and GoDaddy's default builder page is filling the gap.
- This also explains the apparent 404s on `pricing.html`, `about.html`, `support.html`, `privacy.html`, `terms.html` in the page-availability check — those requests hit the GoDaddy placeholder, not the real site, so the result is not meaningful and is superseded by this finding.
- **No action taken** — this requires registrar/DNS changes I don't have credentials for (only Netlify + Supabase tokens were provided, no GoDaddy DNS/registrar access).
- **Live users are currently not able to reach the real app at nearmatch.in.**

### ⚠️ WARN — `create-razorpay-order` has no auth check
- Called with only the public anon key (no user session/JWT) and it returned a real Razorpay order: `{"order_id":"order_THH4m6xpj122hS","amount":29900,"currency":"INR"}`.
- Read `supabase/functions/create-razorpay-order/index.ts`: the function validates `plan` and Razorpay credentials but never verifies the caller's identity (no `supabase.auth.getUser()` check, no user_id tied to the order, no rate limiting).
- Impact: anyone with the (necessarily public) anon key can generate unlimited real Razorpay orders, since the order isn't tied to a paying user. This isn't a fund transfer by itself, but it's unauthenticated write access to a payment provider and should require a valid user JWT.
- **No code change made** — this is a business-logic fix outside the scheduled task's pre-approved auto-fix list, flagged for founder review instead.

### ⚠️ WARN — npm high-severity vulnerability (postcss, via Expo chain)
- `npm audit --json`: 1 high (postcss, via `xcode → @expo/config-plugins → @expo/config → expo-constants → expo-asset`), 10 moderate.
- `npm audit fix --dry-run` shows the only remediation path is `npm audit fix --force`, which would install `expo@57.0.8` — a semver-major breaking bump. Given `AGENTS.md` explicitly calls out that Expo has changed and to check versioned docs before writing code, this was **not auto-applied** and needs founder review/testing before upgrading.

### ⚠️ WARN — `avatars` storage bucket has no size/MIME cap
- Bucket config: `public: true`, `file_size_limit: None`, `allowed_mime_types: None`.
- Storage RLS on `storage.objects` is correctly scoped — INSERT/UPDATE/DELETE all require `(storage.foldername(name))[1] = auth.uid()`, so users cannot write into other users' folders. Public read is expected for profile photos.
- However, with no bucket-level cap, an authenticated user could upload an arbitrarily large or non-image file into their own folder. Recommend setting `file_size_limit` (e.g. 5MB) and `allowed_mime_types` (e.g. `image/jpeg,image/png,image/webp`) on the bucket.

### ℹ️ INFO — `profiles` SELECT policy is broader than the literal spec
- Policy `"profiles are viewable by authenticated users"` has `qual: true` for role `authenticated` — any logged-in user can read any profile row. The audit checklist's generic expectation was "own row only," but this is expected/required for a dating app's swipe/candidate browsing (`get_candidate_profiles` reads from `profiles`). Confirmed anon (unauthenticated) still gets `[]`. Not treated as a defect.
