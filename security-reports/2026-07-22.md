## Findings & Actions Taken

### 🚨 CRITICAL — Storage bucket `avatars` is fully public with no limits
`GET /storage/v1/bucket/avatars` returned `public: true`, `file_size_limit: null`, `allowed_mime_types: null`. Any authenticated (or possibly anon, depending on bucket-level policy) upload path can push arbitrarily large or arbitrarily typed files into a publicly-served bucket. This is a storage-cost and content-safety risk (e.g., non-image files served publicly under the app's domain). Per the audit's auto-fix rules, RLS/storage policy changes are **not** auto-applied — this needs founder review and a decision on size cap (e.g., 5MB) and mime allowlist (`image/jpeg,image/png,image/webp`).

### ⚠️ WARN — npm high-severity vulnerabilities (fixed automatically)
`npm audit` showed 3 high-severity advisories: `brace-expansion`, `js-yaml`, `shell-quote`. Ran `npm audit fix`, which resolved all 3 via an Expo patch bump (`~54.0.34` → `~54.0.36`, non-breaking). Committed as [ba5a6b8](../../commit/ba5a6b8) touching only `package.json`/`package-lock.json`. 11 moderate-severity advisories remain, all requiring `npm audit fix --force`, which would pull in `expo@57.0.7` — a major version bump. Per AGENTS.md's note that Expo has changed significantly across versions, this was **not** auto-applied; it needs a deliberate, tested upgrade, not a scheduled-task auto-fix.

### ⚠️ WARN — `website/refund.html` untracked and 404 in production
The file exists locally (`git status` shows it as `??`, i.e. never committed) and `curl https://nearmatch.in/refund.html` returns 404. Given a refund/cancellation policy is typically required alongside a live Razorpay payment integration, this should be reviewed, committed, and deployed if it's meant to be live.

### Informational — swipes/age_verifications have no direct INSERT policy
By design: writes go through `SECURITY DEFINER` functions (`record_swipe`, `protect_age_verified`) rather than direct table INSERTs. Reviewed `record_swipe()` source — it enforces `auth.uid()`, blocks self-swipes, rate-limits to 60/min, checks the `blocks` table before creating a match, and uses `ON CONFLICT` to avoid duplicate swipe rows. This is correct and intentional, not a gap.

### Informational — `profiles` table is readable by all authenticated users
Policy `profiles are viewable by authenticated users` has `qual: true`, meaning any authenticated user can `SELECT` any profile row. Checked the column list: `id, name, age, gender, bio, avatar_emoji, photo_url, interests, created_at, updated_at, age_verified` — no email, phone, or precise location fields are present, so this is expected/necessary behavior for a dating app's discovery feed, not a leak.
