## Findings & Actions Taken

### 🚨 CRITICAL — `referrals` table: unscoped leftover RLS policy exposes full referral graph
`pg_policies` shows **two** SELECT policies on `public.referrals`:
```
policyname: "users can view referrals they made"   | qual: (referrer_id = auth.uid())   ← correct
policyname: "replace_with_policy_name"              | qual: true                          ← BUG
```
Postgres RLS policies are OR'd together — a row is visible if *any* policy's `qual` passes. Because `replace_with_policy_name` has `qual: true` for role `authenticated`, the properly-scoped policy next to it is completely neutralized: **any logged-in user can `SELECT *` from `referrals` and see every `referrer_id`/`referred_id` pair for the entire user base**, not just their own. The policy name itself (`replace_with_policy_name`) is a template placeholder that was evidently never renamed or given a real `USING` clause before shipping — this reads as an accidental leftover from a migration scaffold, not an intentional design choice.

- **Not exploitable by anonymous users** — anon-key test against `/rest/v1/referrals` returned `[]` (role `authenticated` required), confirmed in the anon access check above.
- **Is exploitable by any signed-up user** — with 12 real accounts on the platform, any one of them can currently pull the full referral graph.
- Table columns exposed: `id`, `referrer_id`, `referred_id`, `created_at` — UUIDs only, no email/phone, but still a real privacy/data-model leak (who-referred-whom is user-linkage data that shouldn't be visible cross-account).
- **No auto-fix applied** — per standing instructions, RLS policy changes are never auto-applied. This needs founder review and a manual `DROP POLICY "replace_with_policy_name" ON public.referrals;` (the remaining `"users can view referrals they made"` policy already covers the legitimate use case).

### ⚠️ WARN — `create-razorpay-order` smoke test creates a real production order every run
Read `supabase/functions/create-razorpay-order/index.ts` to confirm: this endpoint is **intentionally** unauthenticated (anonymous website checkout at nearmatch.in, no app login flow), protected instead by CORS lock to `https://nearmatch.in` and a 5-attempts-per-10-minutes IP-based rate limit (`check_razorpay_order_rate_limit`, verified in DB). This is not a regression — it's the documented design already flagged for founder sanity-check in the 8/3 report.

However, the daily smoke test payload `{"plan":"monthly"}` is a **valid** plan, so instead of hitting the expected `400`, it now returns `200` with a real order:
```json

```
This order was created live on the production Razorpay account as a side effect of today's automated health check (unpaid/uncaptured, so no money moved, but it's a phantom order cluttering the Razorpay dashboard). **This will repeat every day the audit runs** unless the check is changed to send an invalid plan (e.g. `{"plan":"__healthcheck_invalid__"}`) to get the intended `400` without creating a real order. Flagging as a process fix for the check itself, not an app vulnerability.
