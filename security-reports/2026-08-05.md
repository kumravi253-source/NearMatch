## Findings & Actions Taken

### ✅ FIXED — `referrals` table had a placeholder RLS policy granting blanket read access
`pg_policies` showed two SELECT policies on `referrals`:
- `users can view referrals they made` — `qual: (referrer_id = auth.uid())` (correct, restrictive)
- `replace_with_policy_name` — `qual: true`, role `authenticated` (clearly an unfinished template — the name itself is the placeholder Supabase's policy editor inserts by default)

Postgres RLS policies are OR-combined, so the permissive placeholder policy overrode the restrictive one: any authenticated user could read the entire `referrals` table (`id`, `referrer_id`, `referred_id`, `created_at` — UUID pairs, no other PII in this table). Originally flagged for founder review per the standing no-auto-RLS-change rule; **the founder explicitly requested the fix be applied same-day.** Ran `DROP POLICY "replace_with_policy_name" ON public.referrals;` at 2026-08-05 and verified only the correct restrictive policy remains.

### ✅ FIXED — `profiles` RLS did not enforce blocks; direct REST reads bypassed candidate filtering
The `profiles` SELECT policy was `qual: true` for all authenticated users — intentional and expected for a dating app's discovery experience, but the app's actual block-safety logic (excluding blocked/blocking users from view) lived entirely inside the `get_candidate_profiles()` RPC function, not in the RLS policy on `profiles` itself. This meant a client could bypass that protection entirely by querying `/rest/v1/profiles?select=*` directly (e.g. via `id=eq.<blocked-user-id>`) and still retrieve full profile details (name, age, gender, bio, avatar, photo_url, interests, referral_code) of a user who blocked them or whom they blocked.

Originally flagged for founder review per the standing no-auto-RLS-change rule; **the founder explicitly requested the fix be applied same-day.** Ran:
```sql
ALTER POLICY "profiles are viewable by authenticated users" ON public.profiles
USING (
  id = auth.uid() OR NOT EXISTS (
    SELECT 1 FROM public.blocks b
    WHERE (b.blocker_id = auth.uid() AND b.blocked_id = profiles.id)
       OR (b.blocker_id = profiles.id AND b.blocked_id = auth.uid())
  )
);
```
This mirrors the identical bidirectional-block-exclusion pattern already used and proven correct in `get_candidate_profiles()` and the `messages` insert policy. Verified via `pg_policies` that the new `qual` is in place.

**Live spot-check performed same day**, once no real block data was available, using two seeded demo accounts (`Priya` / `7b5a5303-9ba8-4468-91a0-acf2124536a3` and `Arjun` / `76d0883f-ffb5-42f6-ac6d-bc3cd47839dc` — both `@nearmatch.in` test profiles, not genuine users). Inside a transaction: inserted a temporary block row, switched to the `authenticated` role, set `request.jwt.claims` to impersonate each side of the block in turn, ran `SELECT id, name FROM public.profiles`, then `ROLLBACK` (never committed — `SELECT count(*) FROM blocks` confirmed 0 rows afterward, no lasting trace).
- As blocker (Priya): Arjun absent from results; Priya's own row and all 9 other profiles present.
- As blocked party (Arjun): Priya absent from results; Arjun's own row and all 9 other profiles present.

Confirms the policy correctly excludes both directions of a block while preserving self-access and normal browsing of everyone else.

### ✅ CORRECTED — swipe rate limiting exists; original WARN was a false positive
The original audit searched `information_schema.routines` for function names containing `%rate%`/`%limit%` and found nothing for swipes, so it was flagged as a gap. Re-checked by reading `record_swipe()`'s source directly (triggers on `swipes` = none; functions referencing `swipes` = `get_candidate_profiles`, `get_pending_likes`, `record_swipe`) — the limiting logic is inline inside `record_swipe()`, not a separately named function, which is why the name-pattern search missed it:
- **60 swipes/minute** — counts the caller's own swipes in the last 1 minute, raises `rate_limit_exceeded` at ≥60
- **10 likes/24h for free-tier users** — gated on `is_premium(auth.uid())`, raises `daily_like_limit_reached` at ≥10

Verified this can't be bypassed:
- `record_swipe()` is `SECURITY DEFINER` (`prosecdef = true`), but its count query is always scoped to `swiper_id = auth.uid()`, so it can't leak or be manipulated cross-user.
- `swipes` has **no INSERT policy** in `pg_policies` (only the `SELECT` "own rows" policy) — a client cannot bypass the RPC by inserting into `swipes` directly via REST; `record_swipe()` is the only writable path.
- `src/screens/swipe/SwipeScreen.js:66` confirms the app actually calls `.rpc('record_swipe', ...)` for every swipe, not a raw table insert.

No action needed — this check now passes.

### ⚠️ WARN — `create-razorpay-order` edge function returned 200 with only an anon key and no real user auth
Test payload `{"plan":"monthly"}` sent with just the anon key (no logged-in user JWT) returned HTTP 200, not the 400 the task's smoke test expected for a bad/incomplete request. Checked `razorpay_order_attempts` (id 8, created 2026-08-05 02:39:13 UTC, ip 103.208.68.161) — this row was almost certainly created by this smoke test itself (only `ip` + `created_at` columns, no payment data). Same pattern visible from prior days' automated runs (ids 6 and 7 on 2026-08-04). This means the daily health-check itself is writing junk rows into a production rate-limit table — low sensitivity (no PII, just IP+timestamp) but worth the founder confirming whether `create-razorpay-order` should require a valid authenticated JWT before proceeding this far, and whether the healthcheck payload should use a distinguishable test flag so these rows are easy to prune.
